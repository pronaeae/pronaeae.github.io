누적 사용자 수는 약 2.5~3만 명? 비활성 유저를 보존하다가 비활성 상태에서 몇 일 경과되면 Hard Delete를 하여 정확하게 파악은 안된다.
크다면 크고 작다면 작은 서비스였고, 내 첫 작품이라 애정이 많이 갔다.

더 서비스하기에는 서버비와 외부 API 비용이 생각보다 많이 들었고,
취업 준비도 하고 있어 그쪽에 좀 더 힘을 쓰는 게 맞지 않나 싶었다.

유저는 하락세였다가 다시 꾸준히 증가하고 있어서 기분은 좋다.
가난한 미술가라는 말이 있는데, 그런 상황이 된 기분이랄까?

## 운영비용

GCP 120,000원 + a
외부 API $15 + 16,000원 + a

수입이 제일 컸을 때가 280,000원 정도였다.
하지만 +a 에서 마진을 거의 남지 않아 수입은 zero에 육박한다.

## 왜 만들었어?

처음에는 연홍이라는 프로젝트를 보고 명령어가 복잡한 것 같아서 만들었다.
이후 나도 기능을 몇 개씩 추가하면서 똑같이 명령어가 복잡해졌지만, 개선을 하고 있다.

## 네 프로젝트와 다른 서비스의 차이점이 뭐야?

운영 비용을 보면 알겠지만 Typecast의 Voice를 추가하여 더 많은 Voice를 사용할 수 있다.
당시 연홍 봇은 Voice 수가 제한적이였다.

근데 조금 더 서치해보니까 Typecast의 Voice를 지원하는 봇도 있었고 인기도 많았다.
그래서 캐릭터 챗봇 기능까지 얹혔다.

## 느낀점

만드는 것과 **운영하는 것은 완전히 다른 일이었다.**
기능을 붙이는 데 걸린 시간보다, 붙인 다음에 안 죽게 만드는 데 걸린 시간이 훨씬 길었다.

### Supabase 의 유저 인증 관리

`identity` 라는 스키마가 별도로 숨겨져 있었다.
해당 스키마를 사용하면 유저 단에서 위변조가 불가능하여, 유저의 provider id 를 안정적으로 가져올 수 있었다.

뭔가 컴퓨터 구조에서 kernel 이 생각나기도 했다.

### Egress 도 비용이 발생한다

처음에는 그냥 사용해도 무료 버전이라 괜찮을 줄 알았는데 egress 와 cache egress 한도가 초과되었다.
SQL 문에서 모든 정보를 다 가지고 왔는데, 특정 컬럼만 가져오게 하는 것만으로도 효과가 좋았다.

### 유저 정보를 어디까지 암호화해야 하는지?

운영 측에서 따져봤을 때 유저의 정보를 암호화하는 것도 힘들었다.
그래서 유저에 대한 정보를 최소화하였다. 가지고 있지 않으면 지킬 것도 없다.

### Cloudflare 를 쓰면 DNS 를 어떻게 설정해야 하는지?

Google Cloud DNS 를 이용하고 있었는데 Cloudflare를 적용하며 옮겼다.
기존 supabase의 egress로는 부족했는데
R2는 egress도 넉넉하고 편하게 이용이 가능했고 좋았다.

### Nginx 에서도 CORS 설정이 가능하다

프로젝트 레벨에서 CORS 설정을 하고 있었는데 Nginx 로도 가능했다.
Cloudflare SSL 덕분에 SSL 도 손쉽게 적용이 가능했다.
처음 접했을 때 SSL 적용하는 데도 몇 시간이 걸렸던 것 같다.

### 결제는 정합성이 정말 중요하다

여기에 대해 꼼꼼히 알아보지 않았으면, 정합성이 중요한데도 Redis를 먼저 거치는 로직을 생성했을 것이다.
빠르지만 틀릴 수 있는 경로를 결제에 두면 안 된다.

### OOM

캐시 전용 Redis에서 발생했다.
외부 API를 호출하여 똑같은 요청을 처리하는데 동일한 외부 API를 호출하면 비용이 너무 증가할 것 같아서
캐시를 해두었는데, 그게 메모리를 넘겼다.

여기 담기는 건 **잃어도 다시 만들면 그만인 데이터**라 디스크 저장은 아예 껐다.
지킬 필요가 없는 것을 지키느라 디스크와 쓰기 비용을 쓸 이유가 없었다.

문제는 메모리 쪽이었다.
VM 의 RAM 이 1,960MB 인데 `maxmemory` 를 1500mb 로 잡아둔 상태에서 캐시 TTL 을 6시간에서 7일로 늘렸더니,
캐시가 처음으로 그 한도까지 차올랐다.
Redis 의 실제 RSS 는 단편화와 클라이언트 버퍼 때문에 설정값보다 항상 크다.
남은 메모리로 OS 와 나머지 프로세스를 감당하지 못해서 커널이 Redis 를 죽였다.

고친 것은 세 가지다.

- **`maxmemory` 를 1000mb 로** — RAM 의 약 51%. 캐시를 3.6배 키웠을 때 적중률 이득이 14.0% → 15.5% 뿐이었으므로, 줄여서 잃는 것이 작았다
- **eviction 정책을 `allkeys-lru` → `volatile-lru` 로** — 다시 만들기 비싼 키는 일부러 TTL 없이 넣어두는데, `allkeys-lru` 는 그 구분을 무시하고 같이 밀어냈다
- **컨테이너에 메모리 한도를 걸어서** 넘치면 Redis 만 죽고 재시작되게 했다. 한도가 없으면 커널이 VM 전체에서 희생자를 고르기 때문에, sshd 가 죽어 VM 에 손도 못 대는 상황이 될 수 있다

Gateway 로그에 Redis connect 가 실패했다는 로그가 잔뜩 나와서,
**로그 덕에 문제를 빠르게 인식하자마자 고칠 수 있었다.**

### 디스크 풀

로그 데이터들을 제때 정리해주지 않아서 발생했다.
GCP 의 경우 VM 중지 → 디스크 해제 → 용량 증가 → 디스크 설정 후 다시 VM 을 켜주면 되었다.

다만 용량을 늘리는 건 그때뿐이라, 이후에는 오래된 로그가 자동으로 지워지도록 설정했다.
**사람이 기억해서 지워야 하는 것은 언젠가 반드시 잊는다.**

### 모니터링이 생각보다 쉽지 않다

cAdvisor로 컨테이너 메트릭을 모으려 했는데 끝내 되지 않았다.
Docker의 containerd 이미지 스토어와 구조적으로 맞지 않는 문제여서, 설정을 바꿔가며 시도해도 답이 없었다.
결국 재시도하지 않기로 하고 실패한 방법들만 기록해 두었다.

**안 되는 것을 안 된다고 확정하는 데에도 시간이 든다.**

### 서비스에서는 MSA 가 거의 필요없다

사용자가 늘어나는 시점에 혼자 호들갑을 떨며 "이러다 대박나는 거 아니야?" 라는 생각에,
MSA구조로 가지만 DB 와 Redis를 공유하는 아키텍처로 가져갔다.

하지만 전혀 아니었고, 오히려 VM 을 추가로 생성하고 디스크 용량을 증가시켜야 해서 비용이 더 발생한 것 같다.

### 유저들의 지갑을 여는 것은 쉽지 않다

보너스 크레딧을 지급해보기도 하였고 여러 방식을 시도해보았지만,
일상생활에서 꼭 필요한 것이 아니기 때문에 지갑을 열기는 쉽지 않았다.

**가격 책정**도 특히 더욱 더 어려웠다.
기존 경쟁 업체의 유저를 가져오는 것 역시 마찬가지로 쉽지 않았다.

보통 타 서비스 구독을 해지할 때 어떤 이유에서 해지하는지 답변해달라는 사이트가 많은데
나도 그렇게 적용하여 피드백을 좀 더 받아볼 수 있었다.

### 문서화와 기록은 신이다

처음 운영에서 진땀을 뺀 일이 있다. DB마이그레이션 중에 아차... 하는 사이에 데이터가 다 날아가버렸다.

운이 좋게도 DB 백업은 계속 받아두고 있었다.
문제는 **백업을 받은 뒤에 결제한 유저**였다. 그분들 자료가 백업에 없었다.

결제 쪽 감사 기록을 하나씩 대조하며 이 유저의 CustomerKey 는 뭐고 BillingKey 는 뭐지...
하 이건 암호화되어 있네... 인생망했네... 라는 생각으로
되는 데까지 복원한 뒤 데이터를 다시 집어넣었다.

다행히? 결제자가 많지 않아서 한 분 빼고는 복원이 끝났다.

그 사건 이후로 백업 주기와 감사 기록을 매우매우 중요하게 보고 있다.
복구가 되느냐는 결국 **사고가 나기 전에 무엇을 남겨뒀느냐**로 정해진다.

### 판단의 종류는 화면 쪽에서도 같았다

무엇을 미리 만들고 무엇을 나중으로 미룰지, 무엇을 들고 있고 무엇을 버려도 되는지.
서버에서 하던 고민을 프론트엔드에서도 똑같이 했다.

- 기억 그래프를 그리는 캔버스 라이브러리는 무거워서, 정적으로 불러오면 첫 화면 번들에 통째로 실린다.
  `useEffect` 안에서 동적 `import()` 로 청크를 분리했다.
  처음엔 `next/dynamic` 을 썼는데 ref 를 포워딩하지 않아 줌 컨트롤이 깨져서 직접 불러오는 쪽으로 바꿨다.
- 프로필 이미지는 업로드 전에 브라우저에서 WebP 로 변환하고 크기를 줄였다.
  업로드 대역폭과 저장 용량이 같이 줄었다.
- 보이스 샘플 업로드는 413 이 나서, 서버를 거치지 않고 R2 presigned URL로 바로 올리게 바꿨다.

## 그래서 지금은

이 프로젝트를 혼자서 하다보니 내가 지향하는 프론트엔드와는 거리가 좀 먼 것 같다.
그래서 오픈소스로 코드를 조금 수정 후 사용하고 싶은 유저가 셀프호스팅을 통해 서비스를 지속하는 방향으로 할 지 고민하고 있다.
좀 더 프론트엔드 쪽 기술이 필요한 프로젝트를 경험해봐야 할 것 같다.
협업도 하는 게 좋다해서 협업 상대도 구해봐야할 것 같다.
